# Новый session host: как он работает

Обзор на одну страницу, 2026-10-05. Это не спецификация. Подробности и решения — в документах из раздела «Где что лежит».

## Что это

Session host запускает и держит сессии агентских сред: Claude Code, Codex, Muse, позже другие. Он поднимает сессию в нужной папке с нужной целью, даёт подключиться к ней и отключиться, доставляет в неё сообщения («звонок»), паркует, останавливает и восстанавливает. Сегодня это `tb-sessiond` внутри task-board. Мы выносим его в отдельный модуль и продукт — этот репозиторий.

## Как запускается сессия

1. Человек или оркестратор вызывает `curator run claude_code` (позже так же `codex_cli` и канонический env-id Muse из контракта; `claude`/`codex` — это runtime-id хоста, не env-id).
2. Curator собирает план запуска: профиль, модель, effort, разрешения, MCP, сетевой профиль, нативные флаги.
3. Дальше одно из двух:
   - **нативно** (`--native`, по умолчанию, если ничего не настроено) — Curator сам запускает среду, как сейчас;
   - **под хостом** (`--hosted`, или `host: hosted` в операторском конфиге `curator-run-defaults`) — план уходит приёмнику `task-board session launch-plan`, и хост запускает **ровно этот план**, ничего не пересобирая.
4. Без tb-sessiond ничего не ломается: без флага и без настройки хост даже не опрашивается.

Режим разрешений по умолчанию — **yolo**. Его можно поменять в конфиге, явный флаг сильнее конфига.

## Что гарантирует хост

- **Тот же результат, что нативно.** У Claude тот же argv и env, кроме двух объявленных полей: SES-id для уведомлений и UUID сессии. У Codex совпадает результат: модель, разрешения, MCP, env; различия транспорта перечислены явно.
- **Имя сессии и Remote Control** поднимаются как при нативном запуске.
- **Resume и подхват сессий** работают как у `task-board claude`.
- **Проверка до выделения ресурсов.** Неверный план отклоняется с понятным кодом из закрытого реестра ошибок до того, как хост что-либо создаст.
- **Секреты не пишутся на диск.**

## Парковка, рестарт и перезагрузка

1. Хост «звонит» в каждую сессию: паркуйся.
2. Агент доходит до безопасной точки, пишет **park note** и делает ревизию цели с `handoff_ref`. Это и есть сигнал «готов».
3. Хост ждёт всех. Кто не успел к дедлайну, тех паркует принудительно, со снимком доски вместо заметки.
4. Пока идёт замена, **общий замок** не даёт стартовать ни одной новой сессии: ни пробуждениям, ни спавнам, ни восстановлению при входе.
5. Хост выходит, launchd поднимает новую версию.
6. Переходник (позже `keeper up`) ждёт, пока хост поднимется и пройдёт проверки, а среда войдёт в аккаунт; оба ожидания ограничены по времени. Затем он продолжает каждую подходящую сессию через `curator run <env> --hosted resume <SES>` из логин-оболочки. Если сессии нужен Remote Control, после запуска переходник ждёт его регистрации, тоже с ограничением по времени. Только после этого сессия считается вернувшейся и получает отложенные сообщения. Если что-то не прошло, сессия остаётся припаркованной и попадает в отчёт.
7. В конце — отчёт: что вернулось, что нет и почему. Ни одна сессия не теряется молча.

После перезагрузки машины работает тот же механизм, только без парковки. Аварийная остановка — отдельная команда `keeper estop` с подтверждением оператора.

## Версии сред

Curator управляет бинарниками сред:
- **Запуск из кэша.** Сессия запускает копию бинарника из нашего хранилища по хэшу, поэтому автообновление поставщика не может подменить его под живой сессией.
- **Оптимистичный режим по умолчанию.** Новую версию проверяем: подлинность по хэшу поставщика, где он есть; возможности и resume; «чёрный список». Прошла — запускаем и пишем агенту «обновлено X→Y».
- **Автооткат.** Если версия не прошла проверки или упала, сессия поднимается на последней рабочей версии.
- **Режимы `strict` и `pinned`** — по желанию в конфиге.
- **Обновления** ставятся в окне контролируемого рестарта.

## Сеть

Если у сессии есть сетевой профиль, хост сам разрешает его локально, убирает старые прокси-переменные и ставит патч **последним**. Это N-C1b, после пилота. До этого `--hosted --network` честно отказывает.

## Безопасность

- Свой ключ хост держит в файле `0600` вне бэкапов. Это решение с записанными рисками.
- Keychain — позже, после подписи бинарников.
- Тесты никогда не трогают настоящий Keychain.
- Контроль доступа к сокету и токены сессий — первый рефакторинг после выноса (SH2).

## Вендорные отчёты и инварианты

Хост поддерживает вендорный контракт herdr (`report_agent`, `report_agent_session`, `release_agent`): среда, которая его говорит, работает без изменений — в пределах заявленных ограничений §A12 (кадры до 16 КиБ, лимиты источников и хранимого состояния, без сбросов якорей при рестарте процесса внутри запуска). Отчёт — это канал только наблюдений: он меняет отображаемое состояние одного запуска и ничего больше, никогда не становится командой в сессию. Транспорт (`listener | inherited_fd | off`, временно по умолчанию `off`, решение за Иваном) выставляет и зачищает окружение запуска по матрице §A12: при `off` удаляются все `HERDR_*`; детали приёма — в §A12 спецификации.

Три инварианта (решение Ивана, 2026-10-05, R200): криптография и верификация всего входящего в сессию; никакой процесс не может просто так писать в сессию; проект держит большие свармы. Поддержка вендорного контракта никогда их не ослабляет.

## Порядок работ

- **Фаза 1 — Claude**, затем Muse, затем Codex.
- **Готово:** протокол v9 (CR1) и проверка с закрытыми записями (CR2) приняты ревью. CR1 ждёт чтения владельца и окна.
- **Дальше (на ревью Architecture v1):** гибрид (c) вместо выноса как есть; диспозиция SH1 открыта (A-Q1 в `spec/session-host.md`). Цифры 2–4 дня — это as-is альтернатива, не оценка гибрида. Переключение доски — после заморозки перед конференцией (16–19 октября). Сверху Claude-часть: D4 и рестарт (3–5 дней).
- **Демо на трёх ОС** — отдельный трек.
